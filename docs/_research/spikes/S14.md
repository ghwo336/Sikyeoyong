# S14 파우치 지갑으로 D-24 PouchOwner를 앞당길 수 있나 (2026-11-20, 진행 중)

- 질문: 파우치(Pouchi) 임베디드 지갑이 나왔으니 D-24의 `PouchOwner`(사용자 지갑이 소유자)를 앞당길 수 있나. 결제를 파우치 위임(세션 키)으로 옮길 수 있나 (D-25 갱신 판단 자료).
- 번호: 호재 님은 S13으로 요청했지만 S13은 이미 "주인 KYC를 컨트랙트 정책으로 검사"(tech-spec 11, D-16)라 S14로 둔다 (호재 님 동의).
- 범위: 테스트넷(Maroo Testnet, 체인 ID 450815)만. 호재 님 결정 (2026-11-20):
  - SDK는 React SDK(`@shard-lab/nc-waas-react`) 하나로 로그인과 세션 키를 함께 쓴다. 단 이 결정은 문서가 React SDK를 이전 연동(호환 자료)으로 둔다는 사실을 알리기 전에 내려졌다. "새 웹 연동은 현재 Browser SDK와 앱 서버로 시작하세요", "이전 React/Provider와 한 줄 스크립트 예제는 호환 자료예요. 새 임베디드 SDK의 시작점으로 사용하지 마세요" (확인, sdk.md, legacy/react-quickstart). 그래서 다시 물었고, 호재 님 결정 (2026-11-20): **둘 다, 역할을 나눈다.** Browser SDK(`@nc-waas/sdk` beta.8)는 시켜용에 넣을 경로로 확인한다 (로그인, 지갑, 소유자 서명). React SDK는 세션 키 한도와 PCL sender 확인용 일회성 실험으로 `spikes/` 폴더에만 두고 `apps/web`에는 넣지 않는다. GitHub Packages 토큰은 호재 님이 `~/.npmrc`에 넣는다.
  - 승인된 체인 일: SikyeoyongOrders 배포와 컨트랙트 범위 정책 적용.
  - 아직 승인 안 된 일: 파우치 지갑 충전, 파우치 테넌트에 컨트랙트 등록과 세션 승인 clientId 등록. 필요할 때 다시 묻는다.
  - 파우치 운영자의 앱 등록과 가스 대납 승인은 호재 님이 요청한다.
- 출처: pouchi.io/docs (delegation, security, quickstart, sdk/embedded-start, cli, reference/react), `https://pouchi.io/llms-full.txt`, `https://auth.pouchi.io/downloads/README.html`과 `manifest.json` (모두 2026-11-20에 읽음). CLI `@pouchi/cli` 0.1.3 tarball sha256 `ae4e97ace3ca8d31d691d33642f61602ae88a2a13ac128e4ee80100faa11684b` (내려받아 확인, 설치 스크립트 없음).

## 1단계: 문서로 확인한 것 (체인 실행 전)

### 1. 임베디드 로그인으로 사용자 지갑 만들기
- 가입하면 앱 전용 지갑이 생긴다. 이메일 코드와 패스키로 로그인한다. 같은 이메일이라도 앱이 다르면 다른 계정과 지갑이다 (확인, README beta.7, security).
- 키 조각은 파우치 금고 iframe 안에 있고 앱 코드는 키 자료에 접근하지 못한다 (확인, security). 방식은 문서에 없다. 배포 manifest에 `native/mpc-dkls-server`가 있어 MPC(DKLs)로 보인다 (추론).
- 앱 등록은 CLI로 한다: `pouchi login`(이메일 코드, 사람이 넣는다), `apps create`, `apps origins add`, `keys create --env-file .env.pouchi`(0600, git 무시). 테스트 체인 환경이면 `http://localhost:<port>` 같은 루프백 출처를 등록할 수 있다 (확인, cli). 그런데 sdk/embedded-start 준비 절은 "`http://localhost`는 운영 중인 Pouchi SDK와 연결하는 배포 경로가 아니에요"라며 HTTPS 배포를 권한다. 두 문서가 다르다 (확인, cli, sdk/embedded-start. devrel F-19). 실행에서 localhost가 막히면 HTTPS 미리보기 배포가 필요하다.
- 로그인 수단: "앱에서 연 금고는 이메일과 패스키만 제공해요. 소셜 로그인은 없어요." (확인, README). 카카오 같은 OAuth 로그인(`useLoginWithOAuth`)은 이전 연동인 React SDK에만 있다 (확인, reference/react). D-24는 "카카오 로그인으로 앱 안에서 만든 파우치 지갑"을 전제하므로, 현재 Browser SDK로는 카카오 대신 이메일과 패스키가 된다. 시켜용 로그인(카카오, 구글)과 파우치 금고 로그인이 따로 돌게 된다 (추론). PIN은 security.md에 나오지만 README beta.7은 "PIN을 없앴어요"라고 쓴다 (문서끼리 다름).
- 파우치 운영자가 앱 등록과 가스 대납 크레딧을 승인하기 전에는 앱 키를 가입 요청에만 쓸 수 있다 (확인, README "승인 전 사용 범위"). 그래서 2단계와 3단계는 이 승인 뒤에만 된다.
- 가스는 앱이 낸다. 사용자 지갑에서 가스를 빼지 않는다 (확인, security).

### 2. 세션 키(useSessionApproval)로 placeOrder 하나만 허용
- `useSessionApproval`은 React SDK `@shard-lab/nc-waas-react`에만 있다 (확인, reference/react). 현재 웹 SDK `@nc-waas/sdk` beta.8 패키지의 타입 선언에는 `useSessionApproval`, `startSession`, `maxTotalValueWei`가 없다 (확인, 검증 에이전트가 tarball을 받아 확인, sha256은 quickstart 값과 같음). 대신 `delegated-approval.d.ts`(`prepareDelegatedApprovalReview`, `approveDelegatedApprovalReview`: 소유자가 대리인 위임을 승인하는 쪽)가 있다 (확인). React SDK는 지금 GitHub Packages로만 받을 수 있고, 문서는 이것을 이전 연동으로 둔다 (확인, distribution, sdk.md).
- `startSession` 입력: `durationSeconds`(60초~24시간, 기본 1시간), `maxTotalValueWei`, `maxValuePerCallWei`(없으면 총액), `maxCalls`(1~1,000), `contracts`(`{ address, functions }`, 함수 16개까지), `nativeRecipients` (확인, delegation, reference/react).
- 한도는 소유자가 서명한 WaaSWallet 정책에 들어가고 지갑 컨트랙트가 실행마다 검사한다. "앱 코드나 Pouchi 서버가 한도를 올릴 수 없습니다." (확인, delegation)
- `transfer`, `transferFrom`, `approve`, `permit`, `setApprovalForAll`은 세션에 넣을 수 없다 (확인). `placeOrder(uint64,bytes32)`는 payable 함수라 세션에 넣을 수 있어 보인다 (추론).
- 등록하지 않은 컨트랙트 호출은 테넌트 `userCallPolicy`가 막는다 (기본은 등록한 컨트랙트만) (확인, reference/react). 그래서 SikyeoyongOrders를 테넌트에 등록해야 한다 (승인 대기).
- 세션 키는 브라우저 탭에서 만들어지고 탭 밖으로 나가지 않는다. 최대 24시간이다 (확인). 시켜용 서버가 대신 결제하는 구조(지금의 confirm API)와는 다르다. 세션 키 방식이면 결제 서명이 사용자 브라우저에서 일어난다 (추론).
- 한도 안 성공과 한도 밖 실패는 실제 실행으로 확인한다 (대기).

### 2-1. 앱 서버 대리인 (delegation "대리인 종류" 표의 셋째 줄)
- 대리인은 세 종류다: 브라우저 세션 키, PC 지갑 MCP, 앱 서버 (확인, delegation). 앱 서버 대리인은 "앱 운영자 레지스트리 항목"이고 키는 앱 운영자가 KMS나 HSM에 둔다. 실행 함수 `executeDelegatedPolicy`는 "사용 가능", "위임 만들기 함수는 준비 중"이다 (확인).
- 흐름: Pouchi가 정확한 실행 내용을 준비해 digest를 주면 서버의 대리인 키가 서명하고 Pouchi가 제출한다. "서버가 뚫려도 한도 밖의 요청은 체인에서 실패합니다." 결제마다 같은 `requestId`를 쓰면 "같은 ID로 다시 보내도 두 번 결제되지 않음" (확인).
- `@nc-waas/tenant-server-sdk` 배포는 준비 중이고 지금은 nc-waas 저장소 안에 있다 (확인).
- 판단 (추론): 이 경로는 시켜용의 서버 confirm 구조(`POST /orders/:id/confirm`, 사용자 버튼 뒤 서버가 결제)와 `orderRef` 멱등성(규칙 9)에 바로 맞는다. 세션 키와 달리 탭이나 24시간에 묶이지 않는다. 다만 위임 만들기 함수와 서버 SDK가 준비 중이라 지금은 쓸 수 없다. sender는 여기서도 파우치 지갑(4337)일 것이라 3번의 PCL 귀속 질문은 그대로 남는다.

### 3. 그 결제에서 PCL이 보는 sender
- 파우치 지갑은 ERC-4337 지갑(WaaSWallet)이다. 서버 검증 절차가 EntryPoint `0x433709009B8330FDa32311DF1C2AFA402eD8D009`, `UserOperationEvent`, `OwnerCallExecuted`를 대조하라고 한다 (확인, sdk/embedded-start).
- 그러면 `placeOrder`의 `msg.sender`는 세션 키 주소가 아니라 파우치 지갑 컨트랙트 주소다 (추론, 4337 실행 구조). 세션 키는 지갑 컨트랙트가 검사하는 서명자일 뿐이다.
- 컨트랙트 범위 `AGENT_OKRW_TRANSFER_LIMIT_POLICY`는 직접 sender에만 귀속된다 (maroo-facts, 확인). EntryPoint를 거친 호출에서도 그런지는 S12와 같은 질문이다 (미확인). 파우치 지갑이 8004 에이전트로 등록돼 있지 않으면 에이전트 한도 정책이 걸리지 않을 수 있다 (추론). 30일 상한(`PERIODIC_VOLUME_POLICY`)은 (scope, sender, denom) 누적이라 파우치 지갑 주소 기준으로 걸릴 것으로 본다 (추론).
- 실제 영수증과 정책 revert로 확인한다 (대기: 배포, 등록, 충전, 대납 승인).

### 4. 8004 에이전트 신분증을 붙일 자리
| 자리 | 장점 | 문제 |
| --- | --- | --- |
| 세션 키 주소 | 없음 | sender가 되지 않아 PCL 귀속이 안 된다. 탭 안에서만 살고 24시간 뒤 사라진다 (확인과 추론) |
| 파우치 지갑 | sender와 같다 | 사용자 지갑 전체가 "에이전트"가 된다. 8004 소유자가 누구인지(자기 자신?) 꼬인다. 등록 가능 여부 미확인 |
| 별도 에이전트 지갑 (지금 경로 B) | PCL 귀속이 이미 정리돼 있다 (D-25) | 에이전트 키 보관이 남는다 |

- 지금 판단 (추론): D-24의 `PouchOwner`를 앞당기는 데 세션 키는 필요 없다. 소유자 일(TransferLimit, `setAgentPaused`, `bindAgent`, 충전)을 파우치 지갑 서명으로 하는 것이 D-24다. README beta.7의 `createOwnerSigningRequest`와 beta.4의 브리지 `sign`이 "송금과 컨트랙트 호출을 포함한 대기 중 소유자 요청"을 연다고 쓰므로 (확인), 경로 B의 에이전트 지갑은 그대로 두고 그 소유자를 파우치 지갑으로 바꾸는 쪽이 가깝다. 확인할 것: 8004에서 에이전트 소유자를 4337 지갑으로 둘 수 있나, PCL TransferLimit 기록을 그 지갑이 보낼 수 있나 (미확인).

### 5. 회수와 킬 스위치
- "사용자가 위임을 회수하는 기능은 준비 중이에요. 회수를 전제로 한 서비스 적용은 아직 진행하지 마세요." (확인, delegation)
- 그래서 킬 스위치는 `SikyeoyongOrders.setAgentPaused`를 유지한다 (호재 님 지시). 세션 키 방식이면 남은 한도와 기간이 위험 범위이므로 짧은 기간과 작은 `maxTotalValueWei`를 쓴다 (확인, delegation 권고).

## 결론 (임시)
- PouchOwner 앞당기기: 가능성 있음. 세션 키가 아니라 소유자 서명 요청으로 한다. 4번의 확인 두 가지가 관건이다.
- 결제를 파우치 위임으로 옮기기: 세션 키는 구조가 안 맞는다 (최대 24시간, 브라우저 탭 안, 서버 confirm과 다름). 앱 서버 대리인(`executeDelegatedPolicy`)은 구조가 맞지만 위임 만들기 함수와 서버 SDK가 준비 중이라 지금은 못 쓴다. 어느 쪽이든 sender가 4337 지갑이라 컨트랙트 범위 PCL 귀속은 S12와 같은 미확인이다. 회수도 준비 중이다. 실행 결과를 보고 D-25를 갱신한다.

## 정한 것과 남은 것
- SDK: 위 "범위"의 호재 님 결정대로 둘로 나눈다 (Browser SDK는 제품 경로, React SDK는 spikes 실험).
- 문서로 안 풀리는 파우치 질문은 `docs/_research/pouchi-questions.md` 한 곳에 모은다 (S14 끝에 호재 님께 정리해 드림).
- 로그인: 현재 Browser SDK 금고는 이메일과 패스키만 된다. 카카오로 파우치 지갑을 만드는 D-24 전제는 지금 문서로는 이전 연동에서만 된다.

## 문서 문제 (devrel-feedback F-15~F-19에 기록)
- 같은 날 문서에 웹 SDK 버전이 둘이다: sdk/embedded-start는 `0.1.0-beta.5`, quickstart와 manifest는 `0.1.0-beta.8`.
- 세션 키(`useSessionApproval`)는 React SDK에만 있고 현재 웹 SDK에는 없다. 두 SDK의 관계와 함께 쓰는 법이 문서에 없다.
- 지갑 종류(4337 WaaSWallet)와 컨트랙트 호출의 `msg.sender`가 무엇인지 문서가 직접 말하지 않는다. 영수증 검증 절에서만 드러난다.
- 공개 `manifest.json`에 개발자 PC의 로컬 절대 경로가 들어 있다.
- cli.md는 테스트 체인의 localhost 출처를 허용하고, sdk/embedded-start는 localhost가 배포 경로가 아니라고 쓴다.
