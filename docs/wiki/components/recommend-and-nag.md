# 추천과 잔소리 (apps/api/src/modules/recommend, budget)

## 책임
- 추천: 지금 시킬 만한 가게·메뉴 2~3개를 고른다.
- 잔소리: 개인 월 예산 대비 사용률로 경고 단계를 판정한다.
- 결과를 에이전트 런타임에 구조화된 데이터로 넘긴다 (말로 바꾸는 건 런타임).

## 책임 아님
- 주문을 막는 것 (잔소리는 막지 않는다. 막는 건 체인 정책)
- 대사 문장 (`product/mascot-and-voice.md` 규칙에 따라 런타임이 생성)

## 의존과 인터페이스 경계
- 누적 금액 출처: **체인에서 확정된 주문**. 개인 예산 사용액은 인덱서가 `OrderPlaced`/`Refunded` 이벤트로 확정한 `orders`(KST 달력 월, 상태 paid 이상) 합이다. 30일 상한 사용량은 `contractPeriodicVolume(proxy, agent, placeOrderSelector, "atokrw")` (확인된 조회 함수). 인덱서가 확정하지 않은 주문을 합산하지 않는다. DB와 체인이 다르면 체인이 맞다.
- 예산 기준: 개인 월 예산(서버 설정, 기본 300,000 OKRW)과 30일 상한(체인, 500,000 OKRW).
- 코드: `modules/budget/budget.service.ts`의 `BudgetService.getView(userId)`가 `BudgetView`(shared `zBudgetView`)를 만든다. 사용자 예산은 `UsersService`, 레벨·동결·지갑은 `AgentsService`, 이번 달 사용액은 `OrdersService.spentInMonthAokrw`, 30일 사용량은 `ChainReader`로만 받는다 (다른 모듈 저장소를 직접 읽지 않는다). 체인 읽기가 실패하면 숫자를 지어내지 않고 오류를 그대로 낸다.
- 추천 입력: 날씨, 시간대, 대략 위치(1단계는 고정 지역 또는 사용자 입력), 최근 주문, 선호 메모리, 남은 예산, 레벨 한도.
- 추천 코드: `modules/recommend`. `RecommendService.recommend(userId, { craving?, maxPriceAokrw? }, now)`가 입력을 모아 순수 함수 `score.ts`의 `rank()`에 넘긴다. 예산, 레벨, 동결, 30일 사용량은 `BudgetService.getView`, 가게와 메뉴는 `MerchantsService.catalog`(보이는 가게만), 날씨는 `WeatherService`(get_context와 같은 출처, `static`이면 "비", 그 밖은 지어내지 않고 오류), 최근 주문은 `RECENT_ORDERS` 포트(`recent-orders.ts`)로 받는다. 주문 테이블은 orders 모듈 것이라 직접 읽지 않는다. orders가 최근 주문 읽기 함수를 내보내기 전까지 포트는 빈 목록(`NO_RECENT_ORDERS`)이라 선호와 새로움 점수는 모든 가게가 같다 (주문이 결제되는 길도 아직 없어 지금 주문 테이블도 비어 있다). HTTP 경로는 없다 (LLM 도구 `recommend_merchants`만 쓴다).

## 추천 점수 규칙 (코드 기준, tech-spec 3.8)
점수는 정수로만 계산한다. 요소마다 0~100점, 가중치는 정수(35, 20, 20, 15, 10), 금액은 aokrw bigint. 같은 입력이면 어느 기계에서나 같은 순서다.

| 요소 | 가중치 | 점수 |
| --- | --- | --- |
| 예산 맞음 (affordability) | 35, 잔소리 `warn70` 이상이면 55 | 하루 몫 = (개인 예산 − 이번 달 사용액) ÷ 이번 달 남은 KST 날수(오늘 포함, bigint 내림). 가격 ≤ 하루 몫이면 100, 2배 이상이면 0, 사이는 `100 × (2 × 하루 몫 − 가격) ÷ 하루 몫` 내림. 남은 예산이 없으면 모두 0 |
| 날씨 | 20 | 비, 눈, 추움은 국물, 따뜻한. 더움은 면, 냉. 메뉴 태그가 맞으면 100, 가게 태그만 맞으면 50, 아니면 0. 맑음 같은 그 밖의 날씨는 모두 0(중립) |
| 선호 (habit) | 20 | 지난 30일 주문 중 이 카테고리 비율(정수 %, 내림). 기록이 없으면 0. 이 카테고리를 어제와 그제 모두 시켰으면 0 (오늘이면 3일 연속) |
| 새로움 | 15 | 이 가게를 최근 72시간 안에 시켰으면 0, 아니면 100 |
| 먹고 싶은 것 (craving) | 10 | 2글자 이상 단어가 메뉴 이름이나 메뉴 태그에 있으면 100, 가게 이름·카테고리·가게 태그에만 있으면 50, 없으면 0 |

빼는 것과 표시 (명세가 비었거나 다른 곳은 보수적으로 정했다):
- 빼는 것: 미인증 가게, 비활성 가게(`MerchantsService`가 이미 숨김), 영업 시간 밖, 품절 메뉴, `maxPriceAokrw`보다 비싼 메뉴, 30일 사용량 + 가격이 체인 상한을 넘는 메뉴(체인이 거절할 것이라 승인으로도 못 산다), 동결이면 전부(빈 목록과 `frozen: true`).
- 레벨 건당 한도를 넘는 메뉴: 명세 3.8은 "제외", 이 문서는 "승인 필요 표시와 함께만"이다. 둘을 합쳐, 사용자가 먹고 싶은 것으로 말한 메뉴(craving이 맞은 메뉴)일 때만 넣고 `needsApproval`(`OVER_LEVEL_LIMIT`)을 붙인다. 그 밖에는 뺀다. 한도 안 메뉴가 늘 먼저다 (장면 4: "보쌈 대" 45,000원은 레벨 1에서 승인 필요로 나온다).
- 개인 예산을 넘게 되는 메뉴(사용액 + 가격 > 개인 예산): 잔소리는 막지 않으므로 빼지 않고 `needsApproval`(`OVER_PERSONAL_BUDGET`)만 붙인다.
- 먹고 싶은 것이 하나라도 맞으면 맞은 메뉴만 순위를 매긴다(명세는 10% 가중치뿐이지만, "보쌈"이라고 했는데 국밥이 먼저 나오지 않게). 이때는 한 가게가 여러 칸을 차지할 수 있다. 아무것도 안 맞으면 craving은 없던 것처럼 한다.
- craving이 안 맞으면 가게마다 가장 높은 메뉴 하나만 낸다 (같은 가게 메뉴 셋이 나오지 않게).
- 순서: 한도 안 먼저, 점수 높은 순, 같으면 싼 메뉴, 그다음 가게 id, 메뉴 id. 최대 3개.
- 처음 보는 가게의 승인(`NEW_MERCHANT`, `allowed_merchants`)은 아직 반영하지 않는다. approvals 모듈이 허용 가게 읽기 함수를 내보내면 `needsApproval`에 더한다 (worklog 후속).

## 잔소리 규칙
| 단계 | 조건 | 행동 |
| --- | --- | --- |
| 없음 | 사용률 < 70% | 평소대로 |
| 1 | 70% 이상 | 걱정 표정, 한 줄 경고, 추천을 저렴한 쪽으로 |
| 2 | 90% 이상 | 경고 + 남은 금액 명시, 주문 전 한 번 더 확인 |
| 3 | 100% 이상 | 예산 초과 안내. 주문은 사용자가 원하면 진행 (30일 상한 전까지) |
| 체인 상한 | 30일 상한 도달 | 체인이 거절. `resetAt` 안내 |
기준값(70/90/100)은 `packages/shared/src/config/policy.ts`의 `nagThresholdsBps`(bps, [7000, 9000, 10000])이고 판정은 `nagStage`다. 소수를 쓰지 않는다.

## 반드시 지킬 규칙 (MUST)
- "이번 달"의 정의를 화면에 밝힌다: 개인 예산은 달력 월(Asia/Seoul), 체인 상한은 30일 고정 주기. 둘이 다르다는 걸 사용자가 헷갈리지 않게 표시한다.
- 추천 목록에는 체인에 등록된 가게만, 그리고 현재 레벨 한도 안 메뉴를 우선한다. 한도를 넘는 메뉴는 "주인 승인 필요" 표시와 함께만.
- 잔소리 톤은 걱정이다. 비난, 비꼼 금지.
- 같은 단계 잔소리는 한 달에 한 번 (`nag_events` 유니크). 예외: `over100` 이후 주문 직전 확인 카드에는 짧게 붙인다 (tech-spec "3.7 잔소리 계산").
- 잔소리 문구의 숫자는 템플릿과 변수로 만든다. LLM이 숫자를 지어내게 하지 않는다.
- 추천 점수는 서버가 결정적으로 계산하고 LLM은 설명만 한다 (tech-spec "3.8 추천 로직"). 데모는 `WEATHER_PROVIDER=static`으로 재현성을 확보한다.

## 하지 말 것 (MUST NOT)
- 잔소리로 주문을 막지 않는다 (막는 건 체인, 이게 데모의 구분).
- 서버 DB 합계만으로 예산을 판정하지 않는다.
- 위치를 정밀하게 저장하지 않는다 (동 단위 이하).

## 확장 지점
- k-skill `korea-weather`, `kakao-map`을 추천 입력 어댑터로 (`ContextProvider` 인터페이스).
- 2단계 푸시 알림 잔소리.

## 테스트 기준
- 경계값: 69.9%, 70%, 90%, 100%.
- 환불이 누적에서 빠진다.
- 달력 월 경계(말일, 1일)와 30일 주기 경계에서 표시가 맞다.
- 추천 점수의 기대값은 손으로 계산해 테스트에 적는다 (`recommend/score.spec.ts`). 미인증·비활성 가게는 아무리 싸도 안 나온다, 레벨 1에서 4만 5천 원은 승인 필요, 동결이면 빈 목록 (`recommend.service.spec.ts`).
